# Weir - Транспорты

> [English](../en/transports.md) - [Эндпоинты](endpoints.md) - [Безопасность](security.md)

Эндпоинт сам говорит, через какие двери он доступен. Дверей три, и эндпоинт может назвать любое их
сочетание:

| Транспорт | Где | Для чего |
| :-- | :-- | :-- |
| HTTP | `POST /api/{route}` | Для всего. Умолчание и единственная дверь, которую эндпоинт получает, пока не сказано иное. |
| gRPC | сервис `weir.v1.WeirGateway` | Для сервисного клиента, которому нужны мультиплексирование HTTP/2, настоящий стриминг и сгенерированный клиент. |
| WebSocket | `GET /ws` | Для клиента, который делает много мелких вызовов и не хочет платить за соединение и поиск ключа на каждом. |

Транспорт определяет обрамление и то, как приезжает API-ключ. **Больше от двери не зависит ничего**: то
же связывание параметров, тот же конверт ответа, те же требуемые скоупы и гранты, тот же лимит частоты,
та же запись в логе запросов и в аудите. Вызов, который отклонит HTTP, точно так же отклонят gRPC и
WebSocket - и наоборот: эндпоинт, не назвавший транспорт, отвечает там 404, что бы ни было в таблице
маршрутов.

Задаётся у каждого эндпоинта в админке (Эндпоинты -> изменить -> Транспорты) или через admin API:

```json
{ "route": "reports/sales", "httpMethod": "POST", "transports": 5 }
```

`transports` - флаги: `1` HTTP, `2` gRPC, `4` WebSocket, то есть `5` - это HTTP и WebSocket, `7` - все
три. `0` при сохранении отклоняется: эндпоинт, недоступный ниоткуда, - это ошибка, а вывести его из
обслуживания надо через `Enabled: false`.

## HTTP

Не изменился, описан в [Эндпоинты и контракт API](endpoints.md). Эндпоинт, не назвавший HTTP, исключён
и из генерируемого документа OpenAPI - описать его значило бы отдать сгенерированному клиенту маршрут,
который отвечает 404.

## WebSocket

Одна сессия, один API-ключ, один запрос на кадр.

```text
GET /ws
X-Api-Key: wk_live_...
```

Ключ проверяется на рукопожатии, поэтому неаутентифицированный вызывающий сокета не получает вовсе.
Сессия наследует этот один ключ: каждый вызов в ней авторизуется, ограничивается по частоте и
логируется от его имени.

**Кадр-запрос** (текст, JSON):

```json
{ "id": 1, "route": "orders/42", "method": "GET", "body": { "note": "hello" }, "query": { "page": "2" } }
```

| Поле | Значение |
| :-- | :-- |
| `id` | Необязательно. Возвращается обратно как есть - любое значение JSON, - чтобы сопоставлять ответы с запросами. |
| `route` | Обязательно. Маршрут под `/api`, с ведущим слэшем или без. |
| `method` | HTTP-метод, под которым зарегистрирован эндпоинт. Личность эндпоинта - это метод плюс маршрут, поэтому для маршрута под GET здесь нужен `"method": "GET"`. По умолчанию `POST`. |
| `body` | Плоский объект JSON, поля которого - параметры процедуры. |
| `query` | Значения для параметров из query - то, что по HTTP шло бы после `?`. |

Параметры из заголовков читают заголовки **рукопожатия**, а они постоянны всю сессию.

**Кадр-ответ** (текст, JSON), по одному на запрос, в порядке запросов:

```json
{ "id": 1, "body": { "data": [[ ... ]], "output": null, "returnValue": 0, "rowsAffected": -1, "truncated": false, "messages": [] }, "status": 200 }
```

`status` стоит последним намеренно: тело отдаётся потоком по мере чтения строк, поэтому статус
записывается тогда, когда он действительно известен, а не обещается заранее.

Отказ до того, как ушла хоть одна строка, заменяет тело ошибкой:

```json
{ "id": 1, "status": 404, "error": { "title": "Endpoint not found", "detail": "No endpoint is mapped to GET /nope." } }
```

Коды статусов - те же HTTP-коды и значат то же, что на `/api`: 400 неверные параметры, 403 нет прав,
404 нет такого маршрута (или он не обслуживается этим транспортом), 429 превышен лимит частоты, 503
подключение недоступно, 504 сработал таймаут шлюза.

Две вещи следуют из протокола, а не из выбора:

- **Сессия упорядочена.** Один запрос отвечается прежде, чем читается следующий. Сообщение WebSocket
  нельзя перемежать с другим в том же соединении, поэтому «параллельный» ответ пришлось бы буферизовать
  целиком - а именно этой платы транспорт и избегает. Клиент, которому нужны два вызова одновременно,
  открывает две сессии.
- **Отказ на середине тела закрывает сессию** (код закрытия 1011). Строки уже ушли в сеть, и никакое
  окончание не сделает это сообщение корректным JSON, поэтому соединение обрывается так же, как
  обрывается потоковый HTTP-ответ, - чтобы вызывающий отличал обрезанный ответ от полного.

Кадр больше `Weir:DataPlane:MaxRequestBodyBytes` закрывает сессию с кодом 1009 (сообщение слишком
велико): одна дверь не должна принимать то, что отвергает другая.

Браузер не умеет ставить заголовки в рукопожатии WebSocket, поэтому браузер - не адресат этой двери: он
ходит в `/api`. Эта дверь для сервисных клиентов.

## gRPC

Сервис называется `weir.v1.WeirGateway`, контракт лежит в
[`src/Weir.Host/Protos/weir.proto`](../../src/Weir.Host/Protos/weir.proto) - больше клиенту ничего не
нужно.

```proto
service WeirGateway {
  rpc Invoke(InvokeRequest) returns (InvokeReply);
  rpc InvokeStream(InvokeRequest) returns (stream InvokeChunk);
}
```

`Invoke` возвращает весь конверт одним сообщением. `InvokeStream` отдаёт его кусками по мере чтения
строк; склейка кусков по порядку даёт ровно те байты, которые вернул бы `Invoke`, - разбиение есть
свойство провода, а не ответа.

Полезная нагрузка - тот же JSON-конверт, а не сгенерированное сообщение на каждый эндпоинт, и это
решение, а не срез угла: эндпоинты Weir - это метаданные, которые оператор добавляет во время работы,
поэтому генерировать сообщение на этапе сборки не из чего, а шлюз, требующий передеплоя на каждый
эндпоинт, отменял бы сам себя. gRPC здесь вкладывается транспортом.

API-ключ едет в метаданных вызова:

```csharp
var channel = GrpcChannel.ForAddress("https://weir.example.com");
var client = new WeirGateway.WeirGatewayClient(channel);
var metadata = new Metadata { { "x-api-key", "wk_live_..." } };

var reply = await client.InvokeAsync(new InvokeRequest { Route = "orders/42", Method = "GET" }, metadata);
var envelope = Encoding.UTF8.GetString(reply.Envelope.ToByteArray());
```

Отказы приходят статусами gRPC, отображёнными из перечисленных выше: `NOT_FOUND`, `PERMISSION_DENIED`,
`INVALID_ARGUMENT`, `RESOURCE_EXHAUSTED`, `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `UNAUTHENTICATED`,
`INTERNAL`. В detail едут код в форме HTTP и сообщение - то же самое, что пишут лог и аудит, поэтому
одно событие читается одинаково в обоих местах.

Параметры из заголовков читают метаданные вызова (регистр не важен: gRPC приводит ключи к нижнему
регистру на проводе).

### gRPC требует HTTP/2, и из этого следует одно деплойное последствие

Поверх **TLS** делать нечего: ALPN согласует HTTP/1.1 и HTTP/2 на одном порту, поэтому gRPC, data
plane, дверь WebSocket и админка-PWA живут на одном адресе. Это продовый вариант.

Поверх **открытого соединения** порт разделить нельзя: без ALPN согласовывать нечем, и Kestrel отдаёт
HTTP-эндпоинт как HTTP/1.1 (клиенту, который попробует HTTP/2, прилетит `HTTP_1_1_REQUIRED`). Дайте
gRPC отдельный порт средствами самого Kestrel - никакой настройки Weir здесь не участвует:

```json
{
  "Kestrel": {
    "Endpoints": {
      "Http":  { "Url": "http://0.0.0.0:5000" },
      "Grpc":  { "Url": "http://0.0.0.0:5001", "Protocols": "Http2" }
    }
  }
}
```

Тогда `/api`, `/ws` и админка на 5000, а gRPC на 5001. Те же поля переменными окружения:
`Kestrel__Endpoints__Grpc__Url` и `Kestrel__Endpoints__Grpc__Protocols`.

## Какая дверь какому вызывающему

- Браузер, скрипт, curl, всё, что читает документ OpenAPI: **HTTP**.
- Сервис, который зовёт десяток эндпоинтов тысячи раз в минуту: **WebSocket** ради сессии или **gRPC**,
  если нужны ещё мультиплексирование и сгенерированный клиент.
- Задача, читающая очень большой результат: **стриминг gRPC** - он заканчивает сорвавшийся поток
  статусом, а не обрезанным телом.
- То, что вообще не должно быть достижимо из браузера: выключите HTTP и назовите только остальные.
