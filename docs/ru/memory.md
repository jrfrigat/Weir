# Память и большие ответы

> [English](../en/memory.md) - [Настройка](configuration.md) - [Транспорты](transports.md)

Weir читает выборки через `DbDataReader` с `SequentialAccess`, определяет имена колонок и типизированные
методы чтения один раз на набор и пишет UTF-8 JSON без создания объектов строк выборки. Dapper остается
в запросах метаданных и control plane; строки data plane через него не материализуются. Удаление пакета
не убрало бы выделения памяти самими драйверами БД.

## Выбор режима выдачи

Для больших выгрузок выбирайте **Stream**, отключайте кэширование и захват результата на эндпоинте,
а на клиенте читайте HTTP body потоком. Сериализатор сбрасывает ограниченные порции и ожидает отправку;
медленный клиент создает обратное давление. Буферизующий прокси или клиент, разбирающий весь ответ,
может скрывать это поведение. См. [поток через прокси](deployment.md#потоковая-передача-через-прокси).

**Full** формирует конверт до начала передачи. Это позволяет вернуть чистую ошибку до старта HTTP,
но требует хранения полного ответа. Full и заполнения кэша используют сегментированные буферы пула,
а передают ответ ограниченными порциями. Для кэша также нужен неизменяемый снимок байтов с собственным
владением. Размер записи, общий локальный объем, число записей, активные буферы и фоновые сохранения
имеют отдельные лимиты в [настройках](configuration.md). Превышение лимита активных буферов или тела
дает 503 до передачи; ошибка после начала потока обрывает ответ. Слишком большая запись передается,
но не сохраняется в кэш. Лимиты не запускают процедуру повторно и не переключают Full в Stream.

HTTP, WebSocket и потоковый gRPC используют общий конвейер. Unary gRPC требует полного protobuf
сообщения и также учитывается в бюджете буферов. Тестовый вызов админки пишет из движка напрямую,
без дополнительной полной копии ответа. Для больших результатов выбирайте потоковый gRPC.

## Большие значения и оставшиеся затраты

Встроенные коннекторы читают большие объявленные текстовые и бинарные значения порциями из пула.
Небольшие объявленные строки могут использовать `GetString`. Прямой UTF-8 путь PostgreSQL включается
только при подтвержденной UTF-8 кодировке клиента; другие кодировки используют символьный путь.
`GetChars` SQL Server синхронен, поскольку в ADO.NET нет асинхронного аналога; чтение ограничено
порциями с проверкой отмены между ними. Специфичные типы, которые нельзя безопасно читать этими путями,
сохраняют типизированную или резервную обработку.

`MaxBinaryBytes` ограничивает выдаваемые байты BLOB. Остаток дочитывается ограниченными буферами,
чтобы освобождение драйвера не материализовало его целиком. Null, экранирование, границы Unicode,
Base64, наборы результатов и выходные параметры сохраняют контракт конверта. Усеченный ответ не кэшируется.

Это обработка с малыми выделениями, а не обещание нулевых аллокаций или отсутствия Gen 2 GC.
Драйверы, запросы, подключения и резервные пути выделяют память. Расход также зависит от активных
запросов, сетевых буферов, runtime и настроенного кэша. Постоянный RSS при неограниченной конкуренции
невозможен. Бюджет активных буферов ограничивает принадлежащую ему память, а не RSS процесса целиком.
Ограничение конкуренции подключений отдельно защищает БД.

## Память Linux-контейнера

В RSS входят пулы нативного аллокатора и стеки потоков, а также управляемая куча и байты ответов.
Linux может выделить прозрачную крупную страницу размером 2 MiB для редко используемого стека.
Арены нативного аллокатора тоже могут удерживать свободные блоки после завершения запросов.
Ни та, ни другая величина не является живыми данными ответа.

Поставляемый image на glibc задает
`GLIBC_TUNABLES=glibc.pthread.stack_hugetlb=0:glibc.malloc.arena_max=4` до запуска .NET. Стеки pthread
остаются на небольших страницах, а число нативных арен ограничивается четырьмя. Выбор страниц кучи GC
остается за runtime; принудительная сборка или очистка working set не выполняется. Это настройки
запуска image, а не изменяемые из админки runtime settings. Другие хосты и реализации libc сохраняют
собственные настройки, если не заданы отдельно.

Переопределение `GLIBC_TUNABLES` в Docker/Compose заменяет все значение. Для сохранения этих настроек
включайте параметры стеков и арен вместе с остальными tunables. Для других нагрузок или нативных
плагинов, которым нужна большая параллельность аллокатора, сравните другое число арен замерами.
Это не лимит RSS процесса: оставляйте запас для нативных пулов/runtime и задавайте ограничения
ответов, кэша, соединений и контейнера.

## Локальный кэш или Redis

Memory используется по умолчанию. Он хранит сериализованные UTF-8 ответы и ограничивает как байты,
так и количество записей, включая крошечные. Redis необязателен и разделяет снимки между экземплярами;
подключение, namespace, тайм-аут и потолок TTL описаны в [настройках](configuration.md).
RAM сервера Redis отделена от Weir, но получение и отправка снимка требуют временной локальной памяти.
Настройте `maxmemory` и вытеснение Redis. Очистки отсекают поздние заполнения; неполные и усеченные
ответы не публикуются. Фоновые сохранения ограничены по количеству, байтам и времени ожидания.

Дашборд показывает RSS процесса, локально сохраненные данные и общую память среды на одной оси MiB. Данные уже входят
в RSS, прибавлять их к нему не нужно; метаданные кэша и свободные буферы пулов исключены из показателя.
Redis без локального слоя показывает ноль локально сохраненных данных. Неизвестные значения - разрывы.
Общая память - физическая RAM с учетом доступного лимита контейнера/job, а не оставшаяся свободная
память или бюджет кучи GC. Linux учитывает наименьший доступный лимит предков cgroup v1/v2; Windows -
физическую RAM и лимиты текущего job. Другие процессы тоже могут использовать эту емкость. Отключите
общую память в легенде графика, чтобы подстроить масштаб под RSS и кэш. Если необходимый OS-запрос или
доступный лимит нельзя прочитать, значение остается неизвестным, а не нулевым. Отдельный лимит кучи GC
не меняет эту линию. Измерение не вызывает принудительную GC и не сокращает working set процесса.

## Воспроизводимые измерения

Команда `load` sample-клиента вычитывает измеряемые ответы переиспользуемым буфером 16 KiB на worker.
Для больших ответов используйте `--skip-preflight`: обычная предварительная проверка разбирает конверт
на клиенте. `--read-delay 3` задерживает каждые суммарные 16 KiB чтения, `--cancel-after 1000` отменяет
измеряемое окно через секунду. Прогрев идет отдельно. Список задержек и его итоговая отсортированная
копия принадлежат клиенту; его RAM не является измерением памяти сервера. См. [samples](../../samples/README.ru.md).

Необязательный BenchmarkDotNet `MemoryDiagnoser` отделяет затраты сериализатора от драйвера БД.
Он подключает производственный writer и синтетические типизированные reader с переиспользуемыми или
заново материализуемыми строками. Это не HTTP benchmark; обычные тесты его не запускают:

```sh
dotnet run --project benchmarks/Weir.Benchmarks -c Release -- --filter '*Serialize*'
```

Измеряйте сервер отдельно на обеих целевых ОС: с прогревом, реальными типами колонок, конкуренцией,
промахами и попаданиями кэша, медленным чтением и отменой. Сравнивайте аллокации с аллокациями, RSS с RSS.
Короткий замер времени служит диагностикой, а не гарантией пропускной способности.
